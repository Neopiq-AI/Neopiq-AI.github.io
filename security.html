Security and trust, organised around the questions you would ask

ChatAdmin makes real changes in Microsoft Azure, Microsoft Entra, Microsoft 365 and Microsoft Power Platform, so this page is about control: who approves what, under which identity, with which ceilings, and how you can check afterwards. Every answer states what is provable today and labels what is being added. Neopiq holds no security certification and claims no Microsoft endorsement; the last section says exactly what that means.

Why would I sign in through Microsoft? in development

There is no customer sign-in today: the product is reached by a link held by the people who evaluate it, and every change needs an approver key. The first self-service stage we are building is a sign-in with your Microsoft work account. Before you are sent to Microsoft the page will say, in these words: this signs you in to ChatAdmin with your Microsoft work account; ChatAdmin learns your name, sign-in name and your organisation’s tenant id; it does not get access to administer your Microsoft environment; nothing is read or changed in your tenant at this step. Only identity scopes are requested, no directory permission, no client secret exists, and no token is kept at rest. The stages, as they stand.

What permissions does Neopiq request?

From you, as a visitor: none. The demonstration runs on a fictional sample tenant and connects to nothing of yours. When ChatAdmin is operated it acts in each Microsoft area with an identity a Neopiq operator has set up in the environment it administers, and the kind of identity differs by area:

  • Microsoft Entra — the delegated sign-in of a named administrator; ChatAdmin acts with that person’s own directory rights and never more. The header of the chat names whom it acts as.
  • Microsoft 365 — its own application identity (“ChatAdmin Agent M”) with a certificate, no client secret, a fixed list of permissions and the Exchange Administrator role. It never holds a permission on mail, calendar, contact or chat content.
  • Microsoft Azure — the managed identity of the hosted service, holding Contributor on the subscription it operates and a role-assignment permission restricted in Azure itself to an allowlist of roles.
  • Microsoft Power Platform — the delegated sign-in of a Power Platform administrator, through Microsoft’s own first-party sign-in application.

The permissions page lists each area’s reads, changes and ceilings from the code that ships. When your own environment can be connected, every permission will be explained before Microsoft’s consent screen appears: what is requested, which capability needs it, whether it reads or modifies, and whether an administrator must consent. planned

What can it read?

Directory objects and their relationships (users, groups, roles, apps, consent, licences, the directory audit log); mailbox sizes, permissions and memberships (never a message); Teams and SharePoint membership and sharing (never a file’s content); Azure resources, costs, logs and role assignments (never a secret out of a vault); Power Platform environments, apps, flows, connectors and policies (never Dataverse business data or a connection’s credentials). The names and settings it reads are sent to the language model so it can write its answer; anything that looks like a key or password is blanked before it reaches the model or the screen.

What can it change?

Only what is listed per area on the permissions page, only behind a card. The ceilings are in code: no Global Administrator from chat; no Owner or access-administrator role in Azure; no client secret or password, ever; no external mail forwarding; no deletion of a mailbox, team, site or file; deletes that do exist restate the exact name and refuse protected or locked objects; Conditional Access, authentication methods, domains and tenant settings have no tool at all.

When does it execute?

Only after a person clicks Approve on the card for that change. Reads run at once. There is no schedule, no background job and no retry on its own: nothing runs between your turns, and if you ask for “every two minutes” ChatAdmin says in one sentence that it cannot. A declined or timed-out card is final for that request.

How does approval work?

Every change raises an Approve / Reject card naming the area, the environment, every step and parameter (secrets masked), the pre-checks it ran and a five-minute countdown. The human answers it with that area’s approver key — a shared secret handed over on a different channel than the chat link, typed into the page, kept only in that browser tab and sent only inside the one approval it belongs to. Anyone with the link can read and ask; only a key holder can approve. The coordinating layer holds no key and has no approve path; an automated check may only reject. Unanswered for five minutes, a card declines itself. Nothing is ever auto-approved.

Known limit, stated here rather than found by you: the key proves “someone with the key”, not who. Recording which signed-in operator forwarded each decision is part of the Microsoft sign-in work. in development

How do I know which tenant is affected?

Every card names the environment it is about — the tenant or subscription and the identity ChatAdmin acts with there — and the chat header says the same at all times. Today ChatAdmin is connected to one environment, so the answer is also structurally simple. We are adding a check that binds each card to the environment it was raised in and re-reads that environment at approval time: if it has changed, or no longer answers, the approval is refused and nothing is forwarded. in development For operating many customer environments, see the MSP page.

What information does Neopiq store?

Session transcripts: what a person typed, what ChatAdmin answered, every tool call and its bounded result, every card and every decision — one record per event, with secret-shaped values removed before anything is written. They are kept in Neopiq’s own Microsoft Azure storage, reachable only by role-based access, and in the service’s console log. No customer secret is stored: no approver key appears in any transcript, no token is written to disk by the chat, and the administrator sign-ins ChatAdmin uses live on Neopiq’s operator machine and reach the service only as mounted secrets. There is no automatic retention yet: transcripts stay until deleted or until a retention rule is added. planned This website stores nothing: no scripts, no cookies, no form, no account — except the demonstration page, whose one script keeps everything in the page and sends nothing.

How is activity logged?

Three places, independently. The session transcript above. Each area’s own audit record of every decision and action, with secrets redacted. And Microsoft’s own logs in your environment: directory changes appear in the Entra audit log under the administrator the chat acts as, Azure changes in the activity log under the service’s identity, Microsoft 365 changes under the application “ChatAdmin Agent M”. Ask ChatAdmin “who changed what in the last hour?” and it reads the Microsoft Entra and Microsoft Azure logs back; the Microsoft 365 log is read in Microsoft’s own admin center, not through ChatAdmin.

How can access be removed?

Today, by telling Neopiq: the operator revokes the administrator sign-in, disables the application identity, or takes the service down — each ends that area’s access within minutes. For an operated evaluation in your own Microsoft Azure subscription, you create the app registration yourself, upload only Neopiq’s public certificate, and assign the role; deleting that registration or its role assignment removes the access without asking us. built, not yet run with a customer Self-service disconnect and revoke guidance will come with the sign-in stages. planned

Certifications, Marketplace status, endorsements

Neopiq holds no SOC 2 report, no ISO 27001 certification and no security certification of any kind. ChatAdmin is not listed on Microsoft Marketplace (a listing is planned) and Neopiq has no verified-publisher status to show. We do not describe ourselves as compliant with frameworks we have not been audited against, and nothing on this site implies a Microsoft endorsement. If your procurement process requires a certification, we will not pass that gate today, and it is better that both of us know it now. What we do instead is make the claims on this page checkable: the ceilings are enumerated from the shipping code, the approval gate fails closed, and when something is not built yet the site says so.
