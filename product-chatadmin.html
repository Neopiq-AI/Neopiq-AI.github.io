Product · running today · operated by Neopiq · self-service coming

ChatAdmin administers Microsoft Azure, Microsoft Entra, Microsoft 365 and Microsoft Power Platform by conversation — and changes nothing until you say yes

You describe the outcome. ChatAdmin works out which Microsoft areas are involved, reads the real state of your environment, proposes the change on an Approve / Reject card, executes it after your click, reads the result back and tells you what happened. Reads run without interruption; every change waits for a person; an unanswered card declines itself after five minutes.

Availability: ChatAdmin runs in a Neopiq-operated environment, connected by a Neopiq operator to one Microsoft tenant. It is not yet open for self-service sign-up; here is what is coming, stage by stage. To evaluate it, talk to us.

What can I achieve?

The requests an administrator actually gets, answered end to end. You do not have to split them into Microsoft products; ChatAdmin does that and raises one card per area it changes.

A joiner

“Sarah starts in Finance on Monday. Prepare what she needs.” Account, group, licence in Microsoft Entra; team membership and the shared mailbox in Microsoft 365. Two cards, one conversation.

What does using it feel like?

A chat window with one speaker on the other side: ChatAdmin. Under the hood four Microsoft specialists do the work, but you never have to pick one. Here is the shape of every exchange.

  1. You say what you need

    In plain words, with the names you use. If a detail materially affects the operation and cannot be read from the environment, ChatAdmin asks one question; otherwise it proposes the obvious choice and says so on the card.

  2. It inspects before it proposes

    Small grey tool chips show what was read: the users, the group, the free seats, the team. Reads never need approval, so looking around never becomes a habit you click past.

  3. The card

    The Microsoft area, the environment it is about, every step with its parameters (secrets masked), the pre-checks it already ran, and a five-minute countdown. Approve or Reject, answered with that area’s approver key.

  4. Execution and the verified result

    Steps run in order. After each change the object is read back and shown under “Verified after change”. ChatAdmin reports that state, never its intention; if a step failed it says which ones ran and which did not.

  5. The explanation

    What was done, in which area, and what it could not do — a first password it never shows, a role it never assigns, a step that needs the portal.

How it works, in detail

Can I trust it?

The rules below live in the runtime code, outside the language model, and are covered by automated tests. A clever request cannot talk the runtime out of them.

Nothing changes without a click

Every create, update, delete and access change waits for a card. Unanswered for five minutes counts as rejected. There is no auto-approve, no “trusted action” list, no confidence threshold that lets the model decide it is probably fine.

Only a key holder can approve

The link lets a person read and ask. Approving needs that area’s approver key, handed over on a separate channel and typed into the page by the human. The coordinating layer holds no key and cannot approve anything.

Secrets stay secret

ChatAdmin never creates a client secret or password, never reads a secret value out of a vault, never shows a first password, and blanks anything that looks like a key before it reaches the model, the screen or the transcript.

Ceilings in code

Global Administrator is never assigned from chat. Owner is never granted in Azure. Deletes restate the exact name and protected objects are refused. No message is ever read in Microsoft 365. Conditional Access has no tool at all. The full list is on the permissions page.

How does it technically work?

One ChatAdmin, four specialists. Behind the conversation sit four Microsoft-area agents (Azure, Microsoft Entra, Microsoft 365, Power Platform), each a separate service with its own identity, its own tool set, its own guardrails and its own approval card. A coordinating layer reads your request, plans with the tools the agents actually publish, asks them in turn, carries facts between them, and reports back as one voice. The coordinator holds no approval key and has no tool to approve anything: every card is still the agent’s own, answered by you. The language model is used for understanding and planning; the rules that matter — what may be changed, by whom, after what — are enforced in code around it. More on the architecture.
